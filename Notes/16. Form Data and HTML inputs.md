## 1. The Big Picture

A form is essentially a mechanism for collecting **named values** and submitting them.

```html
<form action="/signup" method="POST">
  <input name="email" value="a@b.com" />
  <button type="submit">Submit</button>
</form>
```

The important relationship is:

```text
<input>
   ↓
name="email"
   ↓
"email" = "a@b.com"
   ↓
Form submission / FormData
   ↓
Server
```

### Most important rule

> **`name` identifies form data. `id` identifies an element.**

---

# 2. `<form>`

```html
<form action="/api/signup" method="POST">
  ...
</form>
```

Important attributes:

| Attribute      | Purpose                             |
| -------------- | ----------------------------------- |
| `action`       | URL where the form is submitted     |
| `method`       | HTTP method (`GET` or `POST`)       |
| `target`       | Where to display the response       |
| `enctype`      | How form data is encoded            |
| `autocomplete` | Whether browser autofill is enabled |
| `novalidate`   | Disables browser validation         |

### `method="GET"`

Form data becomes part of the URL:

```text
/search?q=react&page=2
```

Good for:

* Search
* Filtering
* Bookmarkable queries

### `method="POST"`

Data is sent in the request body.

Good for:

* Creating/updating data
* Sensitive-ish form payloads
* Large payloads
* File uploads

> HTTPS is still required for sensitive data. `POST` itself does **not** make data secure.

---

# 3. `name` — The Most Important Attribute

```html
<input name="email">
```

`name` becomes the **key** in submitted form data.

```text
email = "pranay@example.com"
```

Without `name`:

```html
<input value="pranay@example.com">
```

the control generally **does not contribute its value to form submission**.

This applies to:

* Native form submission
* `FormData`
* `URLSearchParams` created from form data
* Many server-side form handling systems

---

# 4. `id` vs `name`

```html
<label for="user-email">Email</label>

<input
  id="user-email"
  name="email"
/>
```

### `id`

Used primarily for **identifying the DOM element**.

Common uses:

```html
<label for="email">Email</label>
```

```css
#email {
  ...
}
```

```js
document.getElementById("email")
```

### `name`

Used primarily for **form data identification**.

```js
formData.get("email")
```

Think:

```text
id   → Which HTML element is this?
name → What is this value called in the form data?
```

They don't need to be the same.

---

# 5. Labels

Always associate labels with inputs when possible.

```html
<label for="email">Email</label>
<input id="email" name="email">
```

`for` → input's `id`.

In React:

```jsx
<label htmlFor="email">Email</label>
<input id="email" name="email" />
```

### Why?

* Accessibility
* Clicking the label focuses/activates the input
* Better screen-reader experience

You can also nest:

```html
<label>
  Email
  <input name="email">
</label>
```

# 7. Text Inputs

```html
<input
  type="text"
  name="username"
  value="pranay"
/>
```

Submitted as:

```text
username=pranay
```

Important attributes:

```html
placeholder="Enter username"
required
minlength="3"
maxlength="20"
pattern="..."
autocomplete="username"
```

### `placeholder` ≠ label

Bad:

```html
<input placeholder="Email">
```

A placeholder should **not replace a label**.

---

# 8. `value`

`value` represents the input's value.

```html
<input name="email" value="a@b.com">
```

When submitted:

```text
email=a@b.com
```

For React, distinguish:

```jsx
value={email}
```

from:

```jsx
defaultValue="a@b.com"
```

---

# 9. Controlled vs Uncontrolled Inputs in React

### Controlled

React owns the current value.

```jsx
const [email, setEmail] = useState("");

<input
  name="email"
  value={email}
  onChange={(e) => setEmail(e.target.value)}
/>
```

Flow:

```text
User types
   ↓
onChange
   ↓
React state
   ↓
value prop
   ↓
input
```

Useful when:

* UI depends on current value
* Real-time validation
* Conditional fields
* Dynamic behavior

### Uncontrolled

The DOM owns the value.

```jsx
<input
  name="email"
  defaultValue=""
/>
```

Read it when needed:

```js
const formData = new FormData(event.currentTarget);
```

Often simpler for ordinary forms.

---

# 10. `FormData`

The browser provides the `FormData` API for extracting form values.

```js
const formData = new FormData(event.currentTarget);
```

Then:

```js
formData.get("email");
```

Example:

```jsx
function handleSubmit(event) {
  event.preventDefault();

  const formData = new FormData(event.currentTarget);

  console.log(formData.get("email"));
}
```

### Important

`FormData` uses **`name`**, not `id`.

```html
<input id="email-field" name="email">
```

```js
formData.get("email");       // ✅
formData.get("email-field"); // ❌
```

---

# 11. Reading FormData

### `get()`

Gets the first value:

```js
formData.get("email");
```

### `getAll()`

Gets all values with that name:

```js
formData.getAll("skills");
```

### `has()`

```js
formData.has("email");
```

### `entries()`

```js
for (const [key, value] of formData.entries()) {
  console.log(key, value);
}
```

### `keys()` / `values()`

```js
formData.keys();
formData.values();
```

### `Object.fromEntries()`

Useful for simple forms:

```js
const data = Object.fromEntries(formData);
```

Example:

```js
{
  email: "a@b.com",
  username: "pranay"
}
```

⚠️ `Object.fromEntries()` can lose information when multiple fields have the **same name**. Use `getAll()` when repeated names matter.

---

# 12. Radio Buttons

Radio buttons use the **same `name`** to form a group.

```html
<input
  type="radio"
  name="gender"
  value="male"
/>

<input
  type="radio"
  name="gender"
  value="female"
/>
```

Only one can be selected.

Submitted data:

```text
gender=male
```

### Why `name` matters

```text
same name → same radio group
different name → different radio groups
```

This is a classic interview question.

---

# 13. Checkboxes

```html
<input
  type="checkbox"
  name="terms"
  value="accepted"
/>
```

If checked:

```text
terms=accepted
```

If unchecked:

> **Nothing is submitted for that checkbox.**

This is an extremely common form gotcha.

### Multiple checkboxes

```html
<input type="checkbox" name="skills" value="react">
<input type="checkbox" name="skills" value="typescript">
<input type="checkbox" name="skills" value="css">
```

If React and CSS are selected:

```text
skills=react
skills=css
```

With `FormData`:

```js
formData.getAll("skills");
// ["react", "css"]
```

---

# 14. `checked`

For checkbox/radio:

```html
<input
  type="checkbox"
  name="terms"
  checked
/>
```

React:

```jsx
<input
  type="checkbox"
  checked={accepted}
  onChange={(e) => setAccepted(e.target.checked)}
/>
```

Use:

```js
event.target.checked
```

rather than:

```js
event.target.value
```

when you want the checkbox's boolean state.

---

# 15. `select`

```html
<select name="country">
  <option value="india">India</option>
  <option value="usa">USA</option>
</select>
```

Submitted:

```text
country=india
```

### `value` matters

```html
<option value="in">India</option>
```

The submitted value is:

```text
in
```

not necessarily the visible text `"India"`.

---

# 16. Multiple Select

```html
<select name="skills" multiple>
  <option value="react">React</option>
  <option value="css">CSS</option>
  <option value="js">JavaScript</option>
</select>
```

Multiple values can be submitted:

```text
skills=react
skills=css
```

Read with:

```js
formData.getAll("skills");
```

# 17. `<textarea>`

```html
<textarea name="message"></textarea>
```

Unlike `<input>`, its initial content is between the tags in HTML:

```html
<textarea name="message">Hello</textarea>
```

React:

```jsx
<textarea
  value={message}
  onChange={(e) => setMessage(e.target.value)}
/>
```

# 18. Buttons

Inside a form:

```html
<button type="submit">Submit</button>
```

### Three useful types

```html
<button type="submit">
<button type="button">
<button type="reset">
```

### Critical interview trap

A `<button>` inside a form **defaults to `type="submit"`** in HTML.

So:

```html
<button>Click</button>
```

can submit the form.

For a button that shouldn't submit:

```html
<button type="button">Click</button>
```

---

# 19. `preventDefault()`

Native form submission normally navigates/reloads the page.

React can intercept it:

```jsx
function handleSubmit(event) {
  event.preventDefault();

  const formData = new FormData(event.currentTarget);
}
```

This gives you SPA-style submission.

> `preventDefault()` prevents the browser's default action; it doesn't stop event propagation.

# 21. `required`

```html
<input name="email" required>
```

The form cannot normally be submitted until a valid value exists.

Checkbox:

```html
<input type="checkbox" required>
```

Useful for terms acceptance.

---

# 22. `disabled` vs `readonly`

### Disabled

```html
<input name="email" disabled>
```

* User can't interact with it.
* Usually **not submitted**.
* Doesn't participate in constraint validation.

### Readonly

```html
<input name="email" readonly>
```

* User can't edit it.
* **Can be submitted**.
* Still participates in form data.

Interview favorite:

> **Disabled controls are excluded from form submission; readonly controls aren't.**

---

# 23. `name` Is Also Important for Form Semantics

A control without `name` is generally not a **successful form control**, meaning its value won't be included in the form submission.

So this:

```html
<input id="email" value="x">
```

is not equivalent to:

```html
<input id="email" name="email" value="x">
```

The second contributes:

```text
email=x
```

---

# 24. Hidden Inputs

Useful for submitting data that isn't directly editable:

```html
<input
  type="hidden"
  name="userId"
  value="123"
/>
```

It participates in form submission.

⚠️ **Never treat hidden input as secure.**

Users can modify it in DevTools.

Anything security-sensitive must be validated server-side.

# 25. File Inputs

```html
<input
  type="file"
  name="avatar"
/>
```

With JavaScript:

```js
const formData = new FormData(form);
const file = formData.get("avatar");
```

The value is a `File` object.

For uploading files, use:

```html
<form
  method="POST"
  enctype="multipart/form-data"
>
```

### `FormData` is particularly useful for file uploads.

---

# 26. `enctype`

Controls how form data is encoded.

### Default

```html
application/x-www-form-urlencoded
```

Looks conceptually like:

```text
email=a%40b.com&name=Pranay
```

### File uploads

```html
multipart/form-data
```

Used when sending files.

### JSON

HTML forms do **not** natively submit forms as:

```text
application/json
```

If you want JSON, JavaScript usually constructs it and sends it with `fetch()`.

---

# 27. Form Submission vs `fetch`

### Native

```html
<form action="/api/users" method="POST">
```

Browser handles the HTTP request.

### JavaScript

```js
const formData = new FormData(form);

fetch("/api/users", {
  method: "POST",
  body: formData,
});
```

For JSON:

```js
const data = Object.fromEntries(new FormData(form));

fetch("/api/users", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify(data),
});
```

⚠️ Don't manually set `Content-Type: multipart/form-data` when sending `FormData` with `fetch`. The browser needs to add the multipart boundary automatically.

# 28. FormData + React

A very clean uncontrolled form:

```jsx
function Signup() {
  function handleSubmit(event) {
    event.preventDefault();

    const formData = new FormData(event.currentTarget);

    const email = formData.get("email");
    const password = formData.get("password");

    console.log({ email, password });
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="email"
        type="email"
        required
      />

      <input
        name="password"
        type="password"
        required
      />

      <button type="submit">
        Sign up
      </button>
    </form>
  );
}
```

For simple forms, this can be preferable to maintaining state for every field.

---

# 29. `event.target` vs `event.currentTarget`

In:

```jsx
<form onSubmit={handleSubmit}>
```

prefer:

```js
new FormData(event.currentTarget)
```

`currentTarget` is the element whose event handler is currently running.

`target` is the element that originally triggered the event.

This distinction becomes important with event bubbling.

---

# 30. Form Data Is Strings (Mostly)

For ordinary inputs:

```html
<input name="age" value="22">
```

```js
formData.get("age");
```

returns:

```js
"22"
```

**not:**

```js
22
```

You need conversion:

```js
const age = Number(formData.get("age"));
```

Similarly, backend validation/parsing should convert and validate types.

Files are an important exception: file inputs produce `File` objects.

---

# 31. React Form Data Gotchas

### Checkbox

Don't do:

```js
formData.get("terms") === "true"
```

unless you explicitly set that value.

HTML checkbox values are typically strings:

```html
<input
  type="checkbox"
  name="terms"
  value="yes"
/>
```

Checked:

```text
"yes"
```

Unchecked:

```text
null
```

You can interpret it:

```js
const accepted = formData.has("terms");
```

if the presence of the checkbox itself represents acceptance.

# 32. Accessibility Basics

Good forms should have:

```text
label
  ↓
input
```

Use:

```html
<label for="email">Email</label>
<input id="email" name="email">
```

For React:

```jsx
<label htmlFor="email">Email</label>
```

For validation errors, consider accessible associations:

```html
<input
  aria-describedby="email-error"

  Invalid email

```

Don't rely solely on color to communicate errors.

# 35. `FormData` Mental Model

Think of `FormData` as:

```text
Map-like collection of name → value pairs
```

But **not exactly a normal JavaScript `Map`**, because:

* It can contain duplicate keys.
* Values can be strings or `File`s.

Hence:

```js
formData.get("skills")
```

→ first value

while:

```js
formData.getAll("skills")
```

→ all values.

# 36. Security

Client-side validation is for **UX**, not security.

This:

```html
<input
  type="number"
  min="18"
>
```

doesn't prevent someone from sending:

```text
age=5
```

directly to your API.

Server must validate:

```text
Client validation
      ↓
Better UX

Server validation
      ↓
Actual security/data integrity
```

Never trust:

* hidden inputs
* disabled fields
* client-side validation
* React state
* values from the browser

# 37. `id`, `name`, `value` — Memorize This

```html
<input
  id="user-email"
  name="email"
  value="p@example.com"
/>
```

```text
id
 ↓
DOM identity / label / CSS / JS

name
 ↓
form-data key

value
 ↓
form-data value
```

So:

```js
formData.get("email")
```

returns:

```text
p@example.com
```

# 38. Interview Rapid-Fire

### Why does an input need `name`?

Because `name` determines the key used when its value participates in form submission / `FormData`.

### Does `id` get submitted?

No. `id` is not the form-data key.

### Why do radio buttons need the same `name`?

To put them in the same mutually-exclusive group.

### Are unchecked checkboxes submitted?

No.

### Are disabled inputs submitted?

No.

### Are readonly inputs submitted?

Yes, assuming they otherwise qualify for submission.

### Does `FormData` convert numbers?

No. Normal input values are strings.

### How do you get multiple values?

```js
formData.getAll("name")
```

### How do you upload files?

Use `FormData` + `multipart/form-data`.

### Should you use React state for every form field?

Not necessarily. Simple forms can often use uncontrolled inputs + `FormData`.

### Is client-side validation sufficient?

No. Always validate on the server.

## ⭐ Final Interview Cheat Sheet

```text
id
→ identifies DOM element
→ label association
→ CSS / DOM APIs
→ should be unique

name
→ identifies form data
→ required for normal form submission
→ groups radio buttons
→ used by FormData

value
→ value submitted for the control

FormData
→ reads form controls by name
→ get() = first value
→ getAll() = all values
→ values are generally strings
→ files become File objects

checkbox
→ unchecked = omitted
→ checked = submitted

radio
→ same name = same group
→ only one selected

disabled
→ not submitted

readonly
→ submitted

button
→ default type inside form is submit
→ use type="button" when it shouldn't submit

GET
→ data in URL
→ useful for searches/filters

POST
→ data in request body
→ useful for mutations

enctype
→ multipart/form-data for files

React
→ controlled = React owns value
→ uncontrolled = DOM owns value
→ FormData is excellent for simple uncontrolled forms

Validation
→ browser/client validation = UX
→ server validation = security/data integrity
```

**The one sentence to remember for interviews:**

> **`id` identifies the element, `name` identifies the submitted field, and `value` is the data associated with that field.**
