# JavaScript Hoisting — From Basics to Advanced

Hoisting is one of those JavaScript concepts that becomes much easier once you understand how JavaScript prepares code before executing it. It connects `var`, `let`, `const`, function declarations, closures, the Temporal Dead Zone, and execution contexts.

One important correction to your notes first:

> Function expressions and arrow functions aren't hoisted like function declarations. But their variable declarations are still processed before execution. The variable's declaration type determines what happens when you access it early.

## 1. What is hoisting?

Hoisting is the behavior in which JavaScript processes declarations before executing the statements in their scope. This affects when identifiers can be accessed and what values they have.

Consider:

```
console.log(a);
var a = 10;
```

Output:

```
undefined
```

Many beginners imagine JavaScript runs this:

```
console.log(a); // undefined
var a = 10;
```

as though it were literally rewritten to:

```
var a;          // declaration processed first
console.log(a); // undefined
a = 10;         // assignment happens here
```

This is a useful mental model, but JavaScript does not literally move the source code. The behavior comes from how the engine creates execution contexts, establishes bindings, initializes declarations, and executes statements.

Now compare:

```
console.log(a);
let a = 10;
```

Output:

```
ReferenceError
```

Both declarations are processed before execution. The difference is that `var` is initialized to `undefined`, while `let` remains uninitialized until its declaration is evaluated.

That's the foundation of hoisting.

## 2. The three things you must distinguish

To understand hoisting completely, separate these concepts.

1\. Declaration

The identifier is established in a scope.

```
var x;
let y;
const z = 3;
```

2\. Initialization

The binding receives its initial value.

```
var x;       // initialized to undefined
let y;       // initialized when this line executes
const z = 3; // initialized when this line executes
```

3\. Assignment

A value is stored in an already initialized binding.

```
let count = 0;
count = 5;
```

The crucial distinction:

- `var`: binding is initialized to `undefined` before the statement executes.
- `let`: binding exists but is uninitialized until its declaration executes.
- `const`: same initial TDZ behavior as `let`, but requires an initializer and cannot be reassigned.
- Function declaration: the function object is available before the declaration's textual position.

## 3. The complete hoisting comparison

This is the table worth memorizing for interviews.

| Declaration            | Before its declaration executes        | Scope                                                         | Can reassign?                       |
| ---------------------- | -------------------------------------- | ------------------------------------------------------------- | ----------------------------------- |
| `var x`                | `undefined`                            | Function or global                                            | Yes                                 |
| `let x`                | TDZ → `ReferenceError`                 | Block                                                         | Yes                                 |
| `const x`              | TDZ → `ReferenceError`                 | Block                                                         | No                                  |
| `function f() {}`      | Function is callable                   | Enclosing function/global scope, subject to declaration rules | Binding behavior depends on context |
| `var f = function(){}` | `undefined`; calling gives `TypeError` | Function or global                                            | Yes                                 |
| `let f = function(){}` | TDZ → `ReferenceError`                 | Block                                                         | Yes                                 |
| `const f = () => {}`   | TDZ → `ReferenceError`                 | Block                                                         | No                                  |

Let's prove each case.

## 4. `var` hoisting

### Example A: Read before declaration

```
console.log(x);
var x = 10;
console.log(x);
```

Output:

```
undefined
10
```

Why?

1. JavaScript establishes the `x` binding and initializes it to `undefined`.
2. The first `console.log` reads that value.
3. `x = 10` executes.
4. The second `console.log` reads `10`.

### Example B: Multiple assignments

```
var score = 10;

function play() {
  console.log(score);
  var score = 20;
  console.log(score);
}

play();
```

Output:

```
undefined
20
```

This is a classic interview trap. The `var score` inside `play()` is function-scoped, so it creates a local binding that shadows the outer `score` throughout the function.

Conceptually:

```
var score = 10;

function play() {
  var score;             // local binding initialized undefined
  console.log(score);    // undefined
  score = 20;
  console.log(score);    // 20
}

play();
```

The first log does not access the global variable.

### Example C: `var` ignores block scope

```
if (true) {
  var message = "Hello";
}

console.log(message);
```

Output:

```
Hello
```

A block created by `{}` does not contain `var` in a separate scope. The binding belongs to the surrounding function or global scope.

Compare with `let`:

```
if (true) {
  let message = "Hello";
}

console.log(message);
```

Output:

```
ReferenceError
```

`let` is block-scoped.

Rule: `var` is function-scoped, not block-scoped.

## 5. `let` and `const`: the Temporal Dead Zone

### What is the TDZ?

The Temporal Dead Zone (TDZ) is the period between entering a scope and the point where a `let` or `const` binding is initialized.

The binding already exists, but accessing it before initialization throws a `ReferenceError`.

```
{
  // TDZ for x begins when this scope is entered.
  console.log(x); // ReferenceError

  let x = 10;     // TDZ ends; x is initialized.
  console.log(x); // 10
}
```

The TDZ is not simply the lines above the declaration. It is a period during execution of the relevant scope.

### Why does JavaScript have a TDZ?

It catches bugs that would otherwise silently read `undefined`, especially when code accesses a variable before its intended initialization.

### Example: TDZ inside a function

```
let value = 100;

function test() {
  console.log(value);
  let value = 200;
}

test();
```

Output:

```
ReferenceError
```

Why doesn't it print `100`?

Because the local `let value` shadows the global `value` throughout the function's scope. At the time of the first log, the local binding is still in its TDZ.

### `const` follows the same TDZ rule

```
console.log(rate);
const rate = 5;
```

Output:

```
ReferenceError
```

And `const` must be initialized when declared:

```
const rate; // SyntaxError
```

### Can you access a TDZ variable using `typeof`?

```
console.log(typeof unknownName); // "undefined"
```

If `unknownName` is genuinely undeclared, `typeof` returns `"undefined"`.

But:

```
console.log(typeof rate);
let rate = 5;
```

throws a `ReferenceError`, because `rate` is a declared binding in its TDZ.

This distinction is extremely useful in interviews.

## 6. Function declarations vs function expressions

This is the heart of your original question.

### A. Function declaration: callable before its definition

```
greet();

function greet() {
  console.log("Hello");
}
```

Output:

```
Hello
```

Function declarations are initialized with their function value during the relevant declaration-instantiation process, making them callable before their textual position.

### B. Function expression assigned to `var`

```
greet();

var greet = function () {
  console.log("Hello");
};
```

Output:

```
TypeError: greet is not a function
```

Why?

- The `var greet` binding exists and initially contains `undefined`.
- The function expression is evaluated only when execution reaches the assignment.
- Before that assignment, `greet()` attempts to call `undefined`.

Conceptual equivalent:

```
var greet; // undefined

greet();    // TypeError

greet = function () {
  console.log("Hello");
};
```

### C. Function expression assigned to `let`

```
greet();

let greet = function () {
  console.log("Hello");
};
```

Output:

```
ReferenceError
```

The binding is in the TDZ when `greet()` executes. JavaScript fails while trying to access the variable, before it can attempt to call it.

### D. Arrow function assigned to `const`

```
greet();

const greet = () => {
  console.log("Hello");
};
```

Output:

```
ReferenceError
```

An arrow function does not get special function-declaration hoisting. It is an expression assigned to a variable. The `const` binding remains uninitialized until its declaration executes.

### Why are the errors different?

Function expression + `var`

## `undefined` → `TypeError`

The binding can be accessed, but its value is not callable.

Function expression + `let` / `const`

## TDZ → `ReferenceError`

The binding cannot be accessed before initialization.

Function declaration

## Function object available

The function can normally be called before its declaration.

Remember this distinction:

- `ReferenceError`: You attempted to access a binding that cannot currently be accessed.
- `TypeError`: The binding was accessible, but the value you tried to call was not a function.

## 7. Function declarations inside blocks

Consider:

```
{
  sayHi();

  function sayHi() {
    console.log("Hi");
  }
}
```

In modern JavaScript, block-level function declarations are generally scoped to their block and can be called within it before their textual position.

```
{
  function sayHi() {
    console.log("Hi");
  }
}

sayHi(); // ReferenceError in modern strict-mode/block-scoped behavior
```

Don't generalize function declarations as always global or always function-scoped. Their scope depends on where they are declared. Legacy, non-strict browser scripts can have special historical behavior for function declarations inside blocks; avoid relying on it.

## 8. Global scope and hoisting

Top-level declarations behave differently depending on whether the code is a classic browser script, an ES module, or another execution environment.

In a classic browser script:

```
var a = 1;
let b = 2;

console.log(window.a); // 1
console.log(window.b); // undefined
```

A top-level `var` in a classic browser script generally creates a property on the global object. Top-level `let` and `const` create global lexical bindings, not properties on `window`.

In an ES module, top-level declarations are module-scoped instead of becoming global `window` properties.

```
<script type="module">
  var a = 1;
  let b = 2;

  console.log(window.a); // undefined
  console.log(window.b); // undefined
</script>
```

This matters in frontend interviews: global scope and the global object are not identical concepts.

## 9. Hoisting in execution contexts

Now for the deeper mental model.

When JavaScript runs a function, it creates an execution context. The engine establishes the bindings needed by that scope before executing the function body.

A simplified model:

```
Call function
    ↓
Create execution context
    ↓
Establish scope bindings
    ↓
Initialize var / function declarations
Keep let / const uninitialized until their declarations
    ↓
Execute statements in order
```

This is a teaching model, not a literal two-pass source-code rewrite.

### Example

```
var outside = "global";

function demo() {
  console.log(outside);
  console.log(inside);

  var inside = "local";
}

demo();
```

Output:

```
global
undefined
```

The local `inside` binding is established and initialized to `undefined` before the body runs. The outer `outside` binding is resolved through the scope chain.

### What is the scope chain?

JavaScript resolves an identifier in its lexical environment:

1. Look in the current scope.
2. If absent, look in the enclosing lexical scope.
3. Continue outward.
4. If no binding is found, a direct read usually throws `ReferenceError`.

```
const country = "India";

function outer() {
  const city = "Indore";

  function inner() {
    console.log(city);
    console.log(country);
  }

  inner();
}

outer();
```

Output:

```
Indore
India
```

The scope chain explains variable lookup. Hoisting explains when bindings are established and initialized. They are related, but they are not the same concept.

## 10. Hoisting with closures and loops

Hoisting and closures often appear together in interview questions.

### `var` inside a loop

```
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Output:

```
3
3
3
```

Why?

- `var` creates one binding for the surrounding function or global scope.
- All three callbacks close over that same `i` binding.
- The loop finishes before the timer callbacks execute.
- By then, `i` is `3`.

### Replace `var` with `let`

```
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Output:

```
0
1
2
```

With `let` in a `for` loop, each iteration has its own relevant binding, so each callback observes the value associated with that iteration.

Interview connection: The result is mainly about scope and closures, not hoisting alone.

## 11. Classes also have a TDZ

Class declarations are lexical bindings and cannot be accessed before their declaration executes.

```
const person = new Person(); // ReferenceError

class Person {}
```

Unlike ordinary function declarations, class declarations are not initialized early enough to be instantiated before their declaration.

Classes also behave differently from functions in strict mode: class bodies are automatically strict.

### Named function expressions

```
const greet = function sayHello() {
  console.log("Hello");
};

greet();    // Hello
sayHello(); // ReferenceError outside the function
```

The variable `greet` is the outer binding. The name `sayHello` is available inside the named function expression itself, but not as an outer binding.

### Imported bindings

ES module imports are established before module body execution:

```
import { greet } from "./greet.js";

greet();
```

Imports are live, read-only bindings. They are not equivalent to copying a value into a local `const`. Module dependency evaluation and cycles can affect whether an imported binding is initialized when accessed.

## 12. Important edge cases

### A. `var` redeclaration

```
var x = 1;
var x = 2;

console.log(x); // 2
```

`var` permits redeclaration in the same scope.

But:

```
let x = 1;
let x = 2; // SyntaxError in the same scope
```

`let` and `const` do not permit duplicate lexical declarations in the same scope.

### B. `let` in a `for` loop

```
for (let i = 0; i < 3; i++) {
  console.log(i);
}
```

Output:

```
0
1
2
```

The `let` binding is block-scoped, and the loop creates per-iteration bindings for the loop variable.

### C. `typeof` with undeclared variables

```
console.log(typeof missing); // "undefined"
console.log(missing);        // ReferenceError
```

`typeof` has a special rule for an unresolvable identifier. That exception does not apply to a lexical binding currently in its TDZ.

### D. Parameters and local variables

```
function test(value) {
  console.log(value);
  var value = 10;
  console.log(value);
}

test(5);
```

Output:

```
5
10
```

The parameter is already initialized with the argument. The `var value` declaration does not create a separate local binding that shadows the parameter; they refer to the same function-scoped binding in this example.

## 13. Common hoisting myths

| Myth                                                 | Correct understanding                                                                                                                     |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `let` and `const` are not hoisted.                   | Their bindings are established before execution but remain uninitialized in the TDZ.                                                      |
| JavaScript physically moves declarations to the top. | Hoisting is a behavior produced by declaration instantiation and execution semantics.                                                     |
| Function expressions are never hoisted.              | Their variable bindings are processed according to `var`, `let`, or `const`; the function value is assigned when the expression executes. |
| Arrow functions behave like function declarations.   | Arrow functions are expressions, not declaration statements.                                                                              |
| All functions can be called before their definition. | Ordinary function declarations generally can; expressions assigned to variables cannot be called before initialization.                   |
| `const` makes an object immutable.                   | It prevents reassignment of the binding, not mutation of the referenced object.                                                           |
| `undefined` means the variable doesn't exist.        | A declared variable can exist and contain `undefined`.                                                                                    |
| Every function declaration is global.                | Its scope depends on where it is declared.                                                                                                |

## 15. Final mental model

When you encounter a hoisting question, ask these four questions in order:

1. What kind of declaration is it? `var`, `let`, `const`, function declaration, class, or import?
2. Which scope owns the binding? Global, function, block, or module?
3. Has the binding been initialized at this point? `undefined`, a function object, or still in the TDZ?
4. What operation is being attempted? Reading a value, assigning it, or calling it as a function?

That reasoning predicts most interview outputs without memorizing isolated examples.

The one-sentence takeaway: Hoisting is about how JavaScript establishes bindings before executing statements; declaration type, scope, and initialization determine whether an early access works, returns `undefined`, or throws an error.
