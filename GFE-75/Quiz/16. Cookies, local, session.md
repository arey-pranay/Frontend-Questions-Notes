# Cookies vs `localStorage` vs `sessionStorage`

## Key Idea

All three store client-side data, but the **biggest interview differences** are:

1. **Who can access it?**
2. **How long does it live?**
3. **Is it automatically sent to the server?**
4. **What security controls are available?**
5. **What scope does it have?**

|                                        | Cookie                          | `localStorage`                | `sessionStorage`       |
| -------------------------------------- | ------------------------------- | ----------------------------- | ---------------------- |
| Storage scope                          | Domain/path + cookie attributes | Origin                        | Origin + tab           |
| Lifetime                               | Session or specified expiry     | Until cleared                 | Until tab/session ends |
| Survives reload?                       | ✅                               | ✅                             | ✅                      |
| Survives browser restart?              | Depends on expiry               | ✅                             | ❌ normally             |
| Sent automatically with HTTP requests? | ✅                               | ❌                             | ❌                      |
| JS access                              | Yes, unless `HttpOnly`          | ✅                             | ✅                      |
| Typical size                           | ~4 KB/cookie                    | Several MB                    | Several MB             |
| String-based?                          | Values are strings              | ✅                             | ✅                      |
| Same-origin tabs share?                | Depends on cookie scope         | ✅                             | ❌                      |
| Main use                               | Server-needed state/auth        | Persistent client preferences | Temporary tab state    |

# 1. Cookies

Cookies are small pieces of data that the browser can **automatically attach to matching HTTP requests**.

```text
Browser
   │
   ├── Cookie
   │
   └── HTTP request ─────────→ Server
                 Cookie: ...
```

A server can create them using:

```http
Set-Cookie: sessionId=abc123
```

or client-side JavaScript can create non-`HttpOnly` cookies:

```js
document.cookie = "theme=dark; Max-Age=604800; Path=/";
```

### Important characteristics

* Small: roughly **4 KB per cookie**
* Can be session or persistent
* Automatically sent with matching requests
* Can be controlled with:

  * `HttpOnly`
  * `Secure`
  * `SameSite`
  * `Expires`
  * `Max-Age`
  * `Domain`
  * `Path`

### Authentication

A common secure pattern is:

```text
HttpOnly
Secure
SameSite=Lax
```

for an opaque session identifier.

`HttpOnly` means:

```js
document.cookie
```

cannot access that cookie.

But remember:

> `HttpOnly` reduces cookie theft through XSS; it does **not** make an XSS vulnerability harmless. Malicious JavaScript can still make authenticated requests as the user.

# 2. `localStorage`

```js
localStorage.setItem("theme", "dark");

localStorage.getItem("theme");

localStorage.removeItem("theme");

localStorage.clear();
```

### Characteristics

* Scoped to the **origin**
* Shared between same-origin tabs/windows
* Persists across browser restarts
* Remains until application/user clears it
* Not automatically sent to the server
* JavaScript can access it

Example:

```js
localStorage.setItem(
  "user",
  JSON.stringify({ id: 1, name: "Ada" })
);

const user = JSON.parse(
  localStorage.getItem("user") ?? "null"
);
```

### Good use cases

* Theme
* Layout preferences
* Recently viewed items
* Non-sensitive client configuration
* Persistent drafts

### Security

Any JavaScript running on your origin can read it.

Therefore, **don't treat `localStorage` as a secure place for secrets or authentication credentials**.

---

# 3. `sessionStorage`

API is almost identical:

```js
sessionStorage.setItem("draft", "hello");

sessionStorage.getItem("draft");

sessionStorage.removeItem("draft");

sessionStorage.clear();
```

The key difference is its **lifetime and scope**.

```text
Tab A
└── sessionStorage A

Tab B
└── sessionStorage B
```

Even if both tabs are on the same origin, they normally have separate `sessionStorage`.

### Characteristics

* Scoped to origin **and browsing context/tab**
* Survives page reloads
* Normally disappears when the tab/window session ends
* Not automatically sent to server
* Accessible to JavaScript

### Good use cases

* Temporary form data
* Multi-step form state
* Tab-specific UI state
* Temporary drafts

---

# The Most Important Interview Difference

### Cookie

```text
Browser → Server
         ↑
     Cookie automatically attached
```

### Web Storage

```text
Browser → Server
         X
    Nothing automatically attached
```

You can manually send:

```js
fetch("/api/data", {
  headers: {
    "X-User": localStorage.getItem("userId")
  }
});
```

but the browser does **not** do this automatically.

# `localStorage` vs `sessionStorage`

The easiest way to remember:

```text
localStorage
→ same origin
→ shared across tabs
→ survives restart

sessionStorage
→ same origin + current tab
→ separate per tab
→ temporary
```

Both:

* store strings
* are synchronous APIs
* are accessible to JavaScript
* have browser-dependent quotas
* can throw `QuotaExceededError`

---

# Security: The Important Interview Trap

Don't simply say:

> "Cookies are secure and localStorage is insecure."

It's more nuanced.

### `localStorage` / `sessionStorage`

Any JavaScript running on the origin can read them.

Therefore:

```text
XSS
 ↓
malicious JS
 ↓
localStorage.getItem(...)
 ↓
secret exposed
```

There is no `HttpOnly` equivalent for Web Storage.

### Cookies

A cookie can be:

```text
HttpOnly
Secure
SameSite
```

For example:

```text
HttpOnly → JS cannot read it
Secure   → HTTPS only
SameSite → helps defend against CSRF
```

However, cookie-based authentication still needs proper CSRF and authorization protections.

---

# Important Next.js / SSR Point

`localStorage` and `sessionStorage` are **browser APIs**.

They aren't available during server-side rendering.

So this is problematic when executed on the server:

```js
const theme = localStorage.getItem("theme");
```

In Next.js, access them only in browser/client-side code, e.g. after mounting when appropriate.

Cookies are different: **server-side code can receive request cookies**, making them suitable for state the server needs during SSR, such as authentication/session information.

# All Three Store Strings

```js
localStorage.setItem("count", 10);

localStorage.getItem("count");
// "10"
```

Not:

```js
10
```

For objects:

```js
localStorage.setItem(
  "user",
  JSON.stringify(user)
);

const user = JSON.parse(
  localStorage.getItem("user") ?? "null"
);
```

# Common Interview Traps

### ❌ "`localStorage` is sent with every request."

No.

Only cookies are automatically attached to matching HTTP requests.

---

### ❌ "`sessionStorage` disappears on refresh."

No.

A page reload normally **preserves** it.

Closing the tab/browsing session normally ends it.

---

### ❌ "`let`/`localStorage` are secure because they're client-side."

No.

Anything in Web Storage is accessible to JavaScript running on the origin.

---

### ❌ "Cookies are always persistent."

No.

Without an explicit expiry, cookies are generally session cookies, although browser session restoration can complicate the practical lifetime.

---

### ❌ "`localStorage` is shared between all browsers/tabs."

No.

It is shared between **same-origin documents**, including tabs/windows in the same browser profile.

`sessionStorage` is additionally scoped to the browsing context.

# Beyond These Three

For larger/structured client-side data:

### IndexedDB

Use for:

* large structured data
* offline application state
* search indexes
* significant amounts of client data

### Cache Storage

Used with Service Workers for:

* cached HTTP responses
* offline/PWA behavior

Don't turn `localStorage` into a fake database by putting huge nested JSON objects inside it.

## TL;DR

> **Cookie:** small, can be `HttpOnly`/`Secure`/`SameSite`, and automatically sent with matching HTTP requests. Best when the server needs the value, especially session identifiers.
>
> **`localStorage`:** persistent, same-origin client storage shared across tabs. Best for non-sensitive preferences/configuration.
>
> **`sessionStorage`:** temporary, tab-scoped storage that survives reloads. Best for state that only belongs to the current browsing session.
>
> **Most important security point:** Web Storage is always JavaScript-accessible; an `HttpOnly` cookie is not.
