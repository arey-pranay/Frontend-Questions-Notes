# Event Delegation

## Key Idea

**Event delegation** means attaching **one event listener to a common ancestor** instead of attaching separate listeners to every child.

It works primarily because of **event bubbling**:

```text
Click child
   ↓
event.target = child
   ↓
event bubbles upward
   ↓
ancestor listener
   ↓
identify relevant child
   ↓
perform action
```

---

## Basic Example

```js
const list = document.querySelector("#item-list");

list.addEventListener("click", (event) => {
  const item = event.target.closest("li");

  if (!item || !list.contains(item)) return;

  console.log(item.textContent);
});
```

Now newly added `<li>` elements automatically work:

```js
list.insertAdjacentHTML("beforeend", "<li>New item</li>");
```

No new listener is required.

---

## `event.target` vs `event.currentTarget`

This is an important interview question.

```js
list.addEventListener("click", (event) => {
  console.log(event.target);        // actual element clicked
  console.log(event.currentTarget); // element with the listener
});
```

If the user clicks:

```html
<li>
  <span>Item 1</span>
</li>
```

then:

```text
event.target        → <span>
event.currentTarget → <ul>
```

### Why use `closest()`?

This is fragile:

```js
if (event.target.tagName === "LI") {
  // ...
}
```

Because the user might click an element **inside** the `<li>`.

Prefer:

```js
const item = event.target.closest("li");
```

This walks upward until it finds the matching element.

# Benefits

### 1. Fewer listeners

Instead of:

```text
1000 items
   ↓
1000 listeners
```

you can have:

```text
1000 items
   ↓
1 ancestor listener
```

This can reduce listener bookkeeping and memory/closure overhead for very large collections.

**Interview nuance:** don't claim delegation is *guaranteed* to make every page faster. Modern browsers handle many listeners well; profile when performance actually matters.

---

### 2. Dynamic elements

This is one of the biggest practical advantages.

```js
container.addEventListener("click", handler);
```

The handler works for descendants added **after** the listener was registered.

You don't need:

```js
newElement.addEventListener(...)
```

every time you add an element.

---

### 3. Centralized logic

For something like a data table:

```html
<button data-action="edit" data-id="42">Edit</button>
<button data-action="delete" data-id="42">Delete</button>
```

You can have one handler:

```js
table.addEventListener("click", (event) => {
  const button = event.target.closest("[data-action]");

  if (!button) return;

  const { action, id } = button.dataset;

  const actions = {
    edit: () => openEditor(id),
    delete: () => confirmDelete(id),
  };

  actions[action]?.();
});
```

This **delegation + `data-*` attributes** pattern is very common in dynamic UIs.

# Not Every Event Bubbles ⚠️

Classic delegation relies on bubbling, so you need to know which events don't bubble.

| Doesn't bubble | Common alternative      |
| -------------- | ----------------------- |
| `focus`        | `focusin`               |
| `blur`         | `focusout`              |
| `mouseenter`   | `mouseover`             |
| `mouseleave`   | `mouseout`              |
| `scroll`       | Usually direct listener |
| `resize`       | Usually direct listener |

### Capture phase

Some non-bubbling events can still be observed through **capture**:

```js
form.addEventListener(
  "focus",
  (event) => {
    console.log(event.target);
  },
  { capture: true }
);
```

For forms, however, `focusin`/`focusout` are often more convenient because they bubble naturally.

# Important Pitfalls

### `stopPropagation()`

If a descendant does:

```js
child.addEventListener("click", (event) => {
  event.stopPropagation();
});
```

the event won't reach the ancestor's delegated handler.

This can make delegation appear "broken."

---

### Validate the matched element

Don't blindly act on every event received by the ancestor:

```js
container.addEventListener("click", (event) => {
  const button = event.target.closest("[data-action]");

  if (!button || !container.contains(button)) return;

  // handle action
});
```

The ancestor can receive clicks from unrelated descendants.

---

### Shadow DOM

For advanced interviews, remember that **Shadow DOM introduces event retargeting and composed-event behavior**, so `event.target` may not always expose the original internal element the way you expect.

---

# React

React also uses centralized event handling internally for many events, but **don't equate React's event system with application-level event delegation**.

You can still deliberately delegate events when working with:

* very large lists
* dynamically generated DOM
* third-party DOM
* tables
* editors
* complex DOM structures

In ordinary React component code, normal:

```tsx
<button onClick={handleClick}>
```

is usually clearer than manually implementing delegation.

---

# Performance Mental Model

Don't memorize:

> "Event delegation = faster."

Instead remember:

```text
Direct listeners
→ simpler target handling
→ potentially many listeners/closures

Delegation
→ one listener
→ target filtering required
→ great for dynamic collections
→ can reduce memory/bookkeeping
```

`closest()` and delegation routing also have a cost, so for a small fixed set of elements, direct listeners may be perfectly appropriate.

---

# Interview Takeaways

* **Event delegation = one ancestor listener handling events from many descendants.**
* Relies mainly on **event bubbling**.
* `event.target` = actual originating element.
* `event.currentTarget` = element where listener is attached.
* Prefer `target.closest(selector)` over checking `target.tagName`.
* Dynamically added descendants automatically work.
* Not every event bubbles.
* `focusin`/`focusout` are bubbling alternatives to `focus`/`blur`.
* `stopPropagation()` can break delegation.
* Delegation can reduce listener/closure overhead, but isn't automatically faster.
* In React, don't use manual delegation everywhere just for performance.

### TL;DR

> **Event delegation = listen once on a stable ancestor, use bubbling to receive descendant events, then use `event.target`/`closest()` to determine what was interacted with. Its biggest practical advantages are dynamic-content support, centralized handling, and potentially fewer listeners.**
