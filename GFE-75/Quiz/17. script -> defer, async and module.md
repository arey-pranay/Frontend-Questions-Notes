# `<script>` vs `<script async>` vs `<script defer>` vs `<script type="module">`

## Key Idea

The `script` element loads and executes JavaScript. The `async` and `defer` attributes control when the script downloads and executes relative to HTML parsing.

The main differences are:

1. Does downloading block HTML parsing?

2. When does execution begin?

3. Is execution order guaranteed?

4. Is the DOM fully parsed when the script runs?

## 2. Regular `<script>`

HTML

```
<script src="app.js"></script>
```

When the browser encounters a classic script:

1. HTML parsing pauses.

2. The script is downloaded if necessary.

3. The script executes.

4. HTML parsing resumes.

   Parse HTML
   ↓
   Find <script>
   ↓
   Pause parsing
   ↓
   Download script
   ↓
   Execute script
   ↓
   Resume parsing

### Example

HTML

```
<h1>Before</h1>

<script src="app.js"></script>

<p>After</p>
```

`app.js` executes after `<h1>` has been parsed but before the `<p>` is parsed.

### Use when

* Code must execute immediately.

* The script needs to affect parsing or the next HTML elements.

* Synchronous execution is explicitly required.

Disadvantage: Large scripts can delay HTML parsing and initial rendering.

## 3. `<script async>`

HTML

```
<script async src="analytics.js"></script>
```

The browser downloads the script in parallel with HTML parsing.

When the download completes, the script executes immediately, potentially interrupting HTML parsing.

```
Parse HTML ────────────────────────► Continue
       │
       └── Download async script
                    │
                    └── Execute immediately when ready
```

### Characteristics

* Downloading does not block HTML parsing.

* Execution can happen before or after parsing completes.

* Multiple async scripts do not guarantee execution order.

* Execution temporarily pauses HTML parsing.

* Async scripts do not generally delay `DOMContentLoaded`.

### Example

HTML

```
<script async src="analytics.js"></script>
<script async src="ads.js"></script>
```

Even though `analytics.js` appears first, `ads.js` might execute first if it finishes downloading earlier.

### Use when

The script is independent and does not rely on:

* Other scripts executing first.

* A fully parsed DOM.

* A specific execution order.

Examples:

* Analytics

* Advertising scripts

* Monitoring and tracking scripts

* Independent third-party integrations

### Avoid when

HTML

```
<script async src="vendor.js"></script>
<script async src="app.js"></script>
```

`app.js` might execute before `vendor.js`, causing errors if `app.js` depends on globals provided by `vendor.js`.

## 4. `<script defer>`

HTML

```
<script defer src="app.js"></script>
```

The script downloads in parallel with HTML parsing, but execution waits until HTML parsing is complete.

```
Parse HTML ────────────────────────► Parsing complete
       │                                      │
       └── Download defer script              │
                                              ▼
                                  Execute deferred scripts
                                  in document order
```

### Characteristics

* Downloads without blocking HTML parsing.

* Executes after the document has been parsed.

* Preserves order between classic deferred scripts.

* Executes before `DOMContentLoaded`.

* The DOM is available when the script executes.

* Deferred scripts can be delayed by stylesheets that block scripts.

### Example

HTML

```
<script defer src="vendor.js"></script>
<script defer src="app.js"></script>
```

Execution order:

```
1. Download vendor.js and app.js in parallel
2. Finish HTML parsing
3. Execute vendor.js
4. Execute app.js
5. Fire DOMContentLoaded
```

### Use when

* The script depends on the DOM being fully parsed.

* Multiple scripts have dependencies or need a specific order.

* You want non-blocking downloads without losing execution order.

### Important

`defer` has no effect on inline classic scripts:

HTML

```
<script defer>
  console.log("defer has no effect here");
</script>
```

It is primarily useful for external classic scripts.

## 5. `<script type="module">`

HTML

```
<script type="module" src="/src/main.js"></script>
```

Module scripts are the standard way to load modern JavaScript modules.

They behave similarly to deferred scripts, with additional module functionality.

### Characteristics

* HTML parsing continues while the module downloads.

* Executes after the document is parsed.

* Module imports are resolved and loaded.

* Dependencies execute before the module that imports them.

* Strict mode is enabled automatically.

* Module scripts use CORS for cross-origin requests.

* Module scripts generally delay `DOMContentLoaded`.

### Example

JavaScript

```
// main.js
import { add } from "./math.js";

console.log(add(2, 3));
```

HTML

```
<script type="module" src="main.js"></script>
```

The browser resolves `math.js` before executing the code that depends on it.

### Strict mode

Module scripts are automatically strict:

JavaScript

```
// Module script
this; // undefined at top level
```

You do not need:

JavaScript

```
"use strict";
```

### Cross-origin modules

Module scripts are fetched using CORS:

HTML

```
<script
  type="module"
  src="https://cdn.example.com/main.js">
</script>
```

The server must provide an appropriate `Access-Control-Allow-Origin` header.

Adding `crossorigin` does not bypass CORS requirements. It controls credential behavior and can help with detailed error reporting.

## 6. `async` with Module Scripts

HTML

```
<script async type="module" src="analytics-module.js"></script>
```

By default, module scripts have deferred behavior.

Adding `async` makes the module execute as soon as its module dependency graph is ready, without waiting for document parsing or other module scripts.

Use this for an independent module entry point where execution order does not matter.

## 7. Execution Timeline

### Regular script

```
HTML parsing ── pause ── Download ── Execute ── resume parsing
```

### Async script

```
HTML parsing ───────────────────────────────►
          └── Download ── Execute immediately
```

Execution can interrupt HTML parsing.

### Deferred script

```
HTML parsing ───────────────────► Complete
          └── Download ────────────────┐
                                       ▼
                               Execute in order
```

### Module script

```
HTML parsing ───────────────────► Complete
          └── Download dependencies
                         │
                         ▼
                  Execute module
```

### Practical recommendation

For modern application code:

HTML

```
<script type="module" src="/src/main.js"></script>
```

For classic scripts that depend on one another:

HTML

```
<script defer src="vendor.js"></script>
<script defer src="app.js"></script>
```

For independent third-party scripts:

HTML

```
<script async src="analytics.js"></script>
```

Build tools such as Vite, Next.js, and other frameworks may generate different script-loading strategies. Inspect the generated HTML rather than assuming the framework uses a specific native attribute.

## 9. Common Mistakes

### Mistake 1: Assuming async scripts preserve order

HTML

```
<script async src="a.js"></script>
<script async src="b.js"></script>
```

`b.js` can execute before `a.js`.

Fix: Use `defer` or modules when order matters.

### Mistake 2: Using async for dependent application scripts

HTML

```
<script async src="vendor.js"></script>
<script async src="app.js"></script>
```

`app.js` may run before `vendor.js` is ready.

Fix:

HTML

```
<script defer src="vendor.js"></script>
<script defer src="app.js"></script>
```

Or use ES modules with imports.

### Mistake 3: Assuming async waits for the DOM

HTML

```
<script async src="dom-script.js"></script>
```

The DOM might not be fully parsed when the script runs.

Fix: Use `defer` if the script requires the complete DOM.

### Mistake 4: Using `document.write()` in async/defer scripts

`document.write()` from asynchronously loaded scripts is ignored by browsers and may generate a console warning.

Avoid `document.write()` in modern applications.

### Mistake 5: Forgetting `type="module"`

HTML

```
<script src="main.js"></script>
```

If `main.js` contains:

JavaScript

```
import { helper } from "./helper.js";
```

The browser throws a syntax error because it is not being treated as a module.

Fix:

HTML

```
<script type="module" src="main.js"></script>
```

## 10. Additional Performance Consideration

`async` and `defer` make downloading non-blocking, but JavaScript execution still occurs on the main thread.

Computationally expensive scripts can still cause:

* Laggy interactions

* Frozen UI

* Delayed rendering

* Long tasks

For certain third-party scripts, tools such as Partytown can move execution into a web worker, although this has compatibility and communication trade-offs.

## Interview Notes

* Regular script: Blocks HTML parsing during download and execution.

* Async: Downloads in parallel and executes as soon as ready; order is not guaranteed.

* Defer: Downloads in parallel and executes after parsing in document order.

* Module: Deferred by default, supports imports, and uses strict mode automatically.

* `async` is suitable for independent scripts.

* `defer` is suitable for ordered classic scripts that need the DOM.

* `DOMContentLoaded` waits for deferred scripts and module scripts, but not async scripts.

* `defer` does not apply to inline classic scripts.

* `async` does not guarantee that the DOM is ready.

* All scripts eventually execute on the main thread unless execution is deliberately moved elsewhere.

## TL;DR

> Regular: Stop parsing → download → execute.
>
> Async: Download in parallel → execute immediately when ready.
>
> Defer: Download in parallel → execute after parsing, in order.
>
> Module: Deferred by default, supports imports and strict mode.

Rule of thumb: Use modules for modern application code, `async` for independent scripts, and `defer` for ordered classic scripts.
