# JavaScript Closures

## Key Idea

A **closure** is a function that retains access to the **lexical environment in which it was created**, even after the outer function has finished executing.

The important point:

> A closure retains access to a **binding/environment**, not a frozen snapshot of its values.

```js
function outer() {
  let count = 0;

  function inner() {
    count++;
    return count;
  }

  return inner;
}

const counter = outer();

console.log(counter()); // 1
console.log(counter()); // 2
```

`outer()` has already finished, but `counter` still has access to `count`.

---

## How Closures Work

JavaScript uses **lexical scoping**.

A function's variable lookup is determined by **where the function is written**, not where it is called.

When a function is created, it retains access to the lexical environment containing the variables it references.

```text
outer()
  │
  ├── count = 0
  │
  └── inner() ──────┐
                     │
                     ▼
              lexical environment
              { count: 0 }
```

After `outer()` returns:

```text
outer() finished
      │
      ▼
lexical environment remains reachable
      │
      ▼
counter() can still access count
```

The environment stays alive as long as a reachable closure still needs it.

---

## Closure Is NOT a Snapshot

This is an important interview point.

```js
function createCounter() {
  let count = 0;

  return () => ++count;
}

const counter = createCounter();

counter(); // 1
counter(); // 2
counter(); // 3
```

The closure does **not** store:

```text
count = 0
```

as a frozen value.

It retains access to the `count` binding, so updates are visible to later calls.

### Separate factory calls have separate state

```js
const counter1 = createCounter();
const counter2 = createCounter();

counter1(); // 1
counter1(); // 2

counter2(); // 1
```

Each call to `createCounter()` creates a **new lexical environment**.

```text
createCounter() ──► Environment A ──► count = 2
                   │
                   └── counter1

createCounter() ──► Environment B ──► count = 1
                   │
                   └── counter2
```

# Why Use Closures?

### 1. Private state / encapsulation

Variables inside the closure aren't directly accessible from outside.

```js
function createBankAccount() {
  let balance = 0;

  return {
    deposit(amount) {
      balance += amount;
    },

    getBalance() {
      return balance;
    },
  };
}

const account = createBankAccount();

account.deposit(100);
console.log(account.getBalance()); // 100

console.log(account.balance); // undefined
```

This creates a simple form of **private state**.

---

### 2. Callbacks and event handlers

Closures allow callbacks to remember variables from their surrounding scope.

```js
function createHandler(name) {
  return () => {
    console.log(`Hello ${name}`);
  };
}

const handler = createHandler("Pranay");

handler(); // Hello Pranay
```

This pattern appears constantly in:

* Event handlers
* `setTimeout`
* Promises
* Array callbacks
* React callbacks
* Async functions

---

### 3. Maintaining state

```js
function createCounter() {
  let count = 0;

  return () => ++count;
}

const counter = createCounter();

counter(); // 1
counter(); // 2
counter(); // 3
```

The state persists between calls without being globally accessible.

---

### 4. Function factories

A function can create specialized functions.

```js
function multiplyBy(x) {
  return (value) => value * x;
}

const double = multiplyBy(2);
const triple = multiplyBy(3);

double(5); // 10
triple(5); // 15
```

`double` remembers `x = 2`; `triple` remembers `x = 3`.

This is closely related to **partial application and currying**.

# Closures in React

Closures are everywhere in React.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

`handleClick` is a closure over:

```text
count
setCount
```

It can access them because they exist in its surrounding lexical scope.

# Stale Closures in React

This is one of the most important practical closure concepts for frontend interviews.

Consider:

```jsx
function Chat() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const interval = setInterval(() => {
      console.log(count);
      setCount(count + 1);
    }, 1000);

    return () => clearInterval(interval);
  }, []);

  return <div>{count}</div>;
}
```

Because the effect runs only once, the interval callback closes over the `count` from that render.

With:

```js
[]
```

the closure continues seeing the initial `count`.

This is a **stale closure**.

---

## Fix 1: Add the dependency

```jsx
useEffect(() => {
  const interval = setInterval(() => {
    setCount(count + 1);
  }, 1000);

  return () => clearInterval(interval);
}, [count]);
```

Now every `count` change creates a new effect/closure.

This is correct, but the interval is recreated whenever `count` changes.

---

## Fix 2: Functional state updater

Usually the simplest solution when you only need to update state:

```jsx
useEffect(() => {
  const interval = setInterval(() => {
    setCount((prev) => prev + 1);
  }, 1000);

  return () => clearInterval(interval);
}, []);
```

The updater receives the latest state, so the callback doesn't need to capture `count`.

---

## Fix 3: `useRef`

Use a ref when a long-lived callback needs to **read the latest value** without causing the subscription/effect to restart.

```jsx
const countRef = useRef(0);

useEffect(() => {
  countRef.current = count;
});

useEffect(() => {
  const interval = setInterval(() => {
    console.log(countRef.current);
  }, 1000);

  return () => clearInterval(interval);
}, []);
```

### Rule

* Only need to **update** state → functional updater.
* Need to **read live state** from a persistent callback → consider a ref.
* Effect genuinely depends on the value → include it in dependencies.

# Closures and `var` in Loops

Classic interview question:

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

// 3
// 3
// 3
```

Why?

`var` is function-scoped, so all three callbacks close over the **same `i` binding**.

The synchronous loop finishes:

```text
i = 0
i = 1
i = 2
i = 3
```

Only afterward do the timer callbacks run.

They all read the same binding:

```text
callback ──┐
callback ──┼──► i = 3
callback ──┘
```

### Fix with `let`

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

// 0
// 1
// 2
```

`let` creates a separate binding for each loop iteration.

```text
callback 1 ──► i = 0
callback 2 ──► i = 1
callback 3 ──► i = 2
```

### Pre-ES6 solution: IIFE

```js
for (var i = 0; i < 3; i++) {
  ((i) => {
    setTimeout(() => console.log(i), 0);
  })(i);
}
```

The IIFE creates a new function scope for each iteration.

# Memoization Using Closures

Closures are useful for keeping a cache private.

```js
function memoize(fn) {
  const cache = new Map();

  return function (...args) {
    const key = JSON.stringify(args);

    if (cache.has(key)) {
      return cache.get(key);
    }

    const result = fn.apply(this, args);

    cache.set(key, result);

    return result;
  };
}
```

Usage:

```js
const square = memoize((n) => {
  console.log("computing...");
  return n * n;
});

square(4); // computing... → 16
square(4); // 16
square(5); // computing... → 25
```

The returned function closes over:

```js
cache
```

so the cache survives between calls while remaining inaccessible directly.

### Important production consideration

A simple `Map` can grow indefinitely.

For long-running applications, caching may require:

* LRU eviction
* TTL
* `WeakMap` for appropriate object-keyed caches
* Explicit cache invalidation

# Closure vs Class

Both can encapsulate state, but they do it differently.

|                   | Closure                                            | Class + `#private`                          |
| ----------------- | -------------------------------------------------- | ------------------------------------------- |
| Private state     | Lexical environment                                | Private class field                         |
| `this` required   | No                                                 | Usually                                     |
| Methods           | New function objects per factory call              | Prototype methods can be shared             |
| Prototype sharing | No                                                 | Yes                                         |
| Inheritance       | Not natural                                        | Supported                                   |
| `instanceof`      | No                                                 | Yes                                         |
| Good for          | Factories, small encapsulated state, callbacks, FP | Domain objects, many instances, inheritance |

### Closure

```js
function makeCounter() {
  let count = 0;

  return {
    inc: () => ++count,
    get: () => count,
  };
}
```

### Class

```js
class Counter {
  #count = 0;

  inc() {
    return ++this.#count;
  }

  get() {
    return this.#count;
  }
}
```

### Practical distinction

If you need a simple factory with private state:

```text
closure → natural
```

If you have many instances sharing behavior or need inheritance/`instanceof`:

```text
class → natural
```

# Can Closures Cause Memory Leaks?

Closures themselves are **not memory leaks**.

The problem occurs when a long-lived reference keeps a closure alive, and that closure keeps large objects alive.

```js
function createHandler(largeObject) {
  return () => {
    console.log(largeObject);
  };
}

const handler = createHandler(largeObject);
```

If `handler` remains reachable for a long time, `largeObject` may also remain reachable.

Common sources include:

* Long-lived event listeners
* Global/module state
* Stores
* Timers
* Caches
* Subscriptions

### Mental model

```text
Long-lived reference
       ↓
    closure
       ↓
captured object
       ↓
cannot be garbage collected
```

Garbage collection is based on **reachability**, not simply whether the outer function has returned.

# Are Closures Synchronous or Asynchronous?

Neither.

A closure is simply a function with access to its lexical environment.

It can execute synchronously:

```js
const fn = createCounter();

fn();
```

or asynchronously:

```js
setTimeout(fn, 1000);
```

The **closure mechanism is independent of when the function executes**.

# Common Interview Traps

### ❌ "A closure stores a copy of the outer variable."

Not exactly.

It retains access to the **lexical binding/environment**.

### ❌ "Closures only happen when an outer function returns."

No.

Closures are a consequence of lexical scoping. Returning a function is simply the easiest way to demonstrate a closure surviving the outer call.

### ❌ "Closures are asynchronous."

No.

A closure can be synchronous or asynchronous.

### ❌ "The outer function's variables disappear when it returns."

They can remain alive if a reachable closure still references them.

### ❌ "Arrow functions are closures."

An arrow function **can be a closure**, but closures are not specific to arrow functions.

```js
function outer() {
  let x = 10;

  return function inner() {
    return x;
  };
}
```

This regular function is also a closure.

# Important Mental Model

Think of a closure as:

```text
Function
   +
Lexical environment it needs
   =
Closure
```

For:

```js
function outer() {
  let count = 0;

  return () => ++count;
}
```

conceptually:

```text
returned function
      │
      └──────► lexical environment
                    │
                    └── count = 0
```

Each call to `outer()` creates a new environment:

```text
outer() ──► Environment A ──► counterA
outer() ──► Environment B ──► counterB
```

Therefore the counters are independent.

If asked **"What is a closure?"**, a strong concise answer is:

> A closure is a function together with access to the lexical environment in which it was created. It allows the function to access variables from its outer scope even after that outer function has finished executing. Closures are commonly used for private state, callbacks, function factories, memoization, and are fundamental to patterns like React hooks.

Then demonstrate:

```js
function createCounter() {
  let count = 0;

  return () => ++count;
}

const counter = createCounter();

counter(); // 1
counter(); // 2
```

The key thing to mention is that the closure retains the **environment/binding**, not a snapshot of `count`.

> **Closure = function + retained access to its lexical environment.**

Remember these four points:

Lexical scope
     ↓
Function captures needed environment

Outer function can finish
