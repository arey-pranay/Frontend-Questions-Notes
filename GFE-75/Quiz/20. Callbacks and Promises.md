# Promises vs Callbacks in JavaScript

## Key Idea

Promises represent the eventual result of a single asynchronous operation—either:

* Fulfilled: Operation succeeded.

* Rejected: Operation failed.

* Pending: Operation has not settled yet.

Promises make asynchronous workflows easier to compose using `.then()`, `.catch()`, `.finally()`, `async/await`, and combinators such as `Promise.all()`.

However, Promises do not automatically cancel operations, represent repeated events, or guarantee that they will settle.

## 1. Callback Hell → Promise Chains

### Callback Hell

Nested callbacks can create a difficult-to-read pyramid structure:

JavaScript

```
getFirstData((data) => {
  getSecondData(data, (data) => {
    getThirdData(data, (result) => {
      console.log(result);
    });
  });
});
```

Problems:

* Deep nesting.

* Error handling can become repetitive.

* Difficult to maintain and extend.

* Callback contracts may be inconsistent.

### Promise Chain

JavaScript

```
getFirstData()
  .then(getSecondData)
  .then(getThirdData)
  .then((data) => {
    console.log(data);
  })
  .catch((error) => {
    console.error("Error:", error);
  });
```

Each `.then()` returns a new Promise, allowing the next operation to receive the previous result.

> Modern JavaScript usually uses `async/await`, which is built on Promises and often reads more like synchronous code.

## 2. Pros of Promises

### 1. More Readable Sequential Code

JavaScript

```
async function loadData() {
  try {
    const first = await getFirstData();
    const second = await getSecondData(first);
    const third = await getThirdData(second);

    console.log(third);
  } catch (error) {
    console.error("Error:", error);
  }
}
```

Interview point: Promises flatten nested asynchronous workflows and provide a consistent way to pass results between operations.

### 2. Easier Parallel Operations

Use `Promise.all()` when multiple independent operations can run concurrently.

JavaScript

```
const results = await Promise.all([
  getData1(),
  getData2(),
  getData3(),
]);
```

Equivalent `.then()` style:

JavaScript

```
Promise.all([getData1(), getData2(), getData3()])
  .then((results) => {
    console.log(results);
  })
  .catch((error) => {
    console.error("Error:", error);
  });
```

Important behavior:

* All operations are started when their functions are called.

* Results preserve the order of the input Promises.

* Rejects when any input Promise rejects.

* Does not cancel the other operations automatically.

### 3. Centralized Error Handling

JavaScript

```
getFirstData()
  .then(getSecondData)
  .then(getThirdData)
  .catch((error) => {
    console.error(error);
  });
```

A rejection or a thrown error in the chain can propagate to a later `.catch()`.

However, the error handler must actually be connected to the Promise chain. Detached Promises can result in unhandled rejections.

### 4. Guaranteed Cleanup with `finally()`

`finally()` executes when a Promise settles, whether fulfilled or rejected.

JavaScript

```
fetchData()
  .then((data) => {
    renderData(data);
  })
  .catch((error) => {
    showError(error);
  })
  .finally(() => {
    hideLoadingSpinner();
  });
```

Common uses:

* Hiding loading indicators.

* Resetting UI state.

* Releasing temporary resources.

* Cleaning up after an operation.

`finally()` does not receive the fulfillment value or rejection reason directly.

### 5. A Stricter Settlement Contract

A Promise can settle only once:

JavaScript

```
const promise = new Promise((resolve, reject) => {
  resolve("Success");
  reject("Failure"); // Ignored
});
```

The Promise remains fulfilled with `"Success"`.

Promise reactions also run asynchronously as microtasks, creating a more consistent execution model than callback APIs that might invoke callbacks synchronously or asynchronously.

## 3. Cons of Promises

### 1. No Automatic Cancellation

A Promise represents an outcome, not cancellation.

For example, `fetch()` can be cancelled using `AbortController`:

JavaScript

```
const controller = new AbortController();

fetch("/api/data", {
  signal: controller.signal,
});

// Cancel the fetch operation
controller.abort();
```

The API must support cancellation, and the caller must pass and manage the `AbortSignal`.

> Rejecting a Promise does not automatically stop the underlying operation.

### 2. `Promise.all()` Does Not Cancel Remaining Operations

JavaScript

```
await Promise.all([
  fetch("/api/slow"),
  fetch("/api/failing"),
]);
```

If one Promise rejects, `Promise.all()` rejects early, but other requests may continue running.

If cancellation is required, use an explicit cancellation mechanism such as `AbortController`.

### 3. Promises Represent One Result
The key distinction is **one eventual result vs. an ongoing sequence of values**.

 - **Promise** → represents one asynchronous result that settles once (`fulfilled` or `rejected`).
- **Event listener** → handles repeated events pushed by something like the DOM.
- **Async iterator / stream** → lets you consume multiple asynchronous values sequentially over time, typically with `for await...of`.
- **Observable** → represents a potentially unbounded sequence of values and is designed for reactive programming, where consumers subscribe and react as values arrive.

 For example:

```
// Promise: one result
const response = await fetch("/api/data");

// Event listener: repeated events
button.addEventListener("click", handler);

// Async iterator: multiple async values
for await (const value of stream) {
  console.log(value);
}

// Observable: reactive sequence
observable.subscribe(value => {
  console.log(value);
});
```

 So a useful rule of thumb is:

 > **Promise = “give me the result.”**\
>  **Stream/Observable = “keep giving me results as they arrive.”**
> 
Example:

JavaScript

```
button.addEventListener("click", handleClick);
```

A click listener can run repeatedly, whereas a Promise settles only once.

### 4. Forgotten `return` or `await`

#### Problem

JavaScript

```
function saveData() {
  apiCall().then(() => {
    console.log("Saved");
  });
}
```

The outer function does not return the Promise, so callers cannot track completion or catch its errors through `saveData()`.

#### Fix

JavaScript

```
function saveData() {
  return apiCall().then(() => {
    console.log("Saved");
  });
}
```

Or:

JavaScript

```
async function saveData() {
  await apiCall();
  console.log("Saved");
}
```

Interview point: Always return or await Promise-based work when the caller needs completion and error propagation.

### 5. Long Chains Can Hide Context

A long Promise chain may make it difficult to determine which operation failed.

Improve debugging by:

* Using meaningful function names.

* Adding contextual error messages.

* Handling errors at appropriate boundaries.

* Avoiding unnecessarily complicated chains.

### 6. Incorrect Callback-to-Promise Conversion

Promises are suitable when a callback represents one eventual result.

They are not a direct replacement for APIs that produce repeated values.

JavaScript

```
// Repeated events: do not wrap as a single Promise
element.addEventListener("click", handler);
```

Wrapping a repeated callback API in a Promise generally captures only the first event and leaves the listener active unless it is explicitly removed.

## 5. Important Promise Combinators

|
Method

|

Behavior

|
| --- | --- |
|

`Promise.all()`

|

Fulfilled when all fulfill; rejects on the first rejection

|
|

`Promise.allSettled()`

|

Waits for every Promise and reports each outcome

|
|

`Promise.race()`

|

Settles when the first input settles

|
|

`Promise.any()`

|

Fulfills when the first input fulfills; rejects if all reject

|

Use the combinator based on the required behavior rather than assuming all parallel operations should use `Promise.all()`.

## 6. Interview Notes

* Promises do not make asynchronous work automatically parallel. Parallelism depends on when operations are started.

* `Promise.all()` preserves input order in its result array.

* `Promise.all()` rejects early but does not cancel remaining work.

* A Promise is not a stream and cannot be reused for repeated events.

* Promises do not guarantee settlement; a Promise can remain pending forever.

* `async` functions always return a Promise.

* Returning a Promise from `.then()` adopts that Promise's eventual state.

* Errors thrown inside a `.then()` callback become rejections of the returned Promise.

* Promises do not inherently improve CPU-heavy work; JavaScript execution can still block the main thread.

* `finally()` is useful for cleanup regardless of success or failure.

### Strong Interview Answer

> Promises provide a standardized abstraction for one eventual asynchronous result, making sequential and parallel workflows easier to compose through `.then()`, `async/await`, and combinators. They improve error propagation and avoid callback nesting, but they do not provide automatic cancellation or support repeated events. Developers must also return or await Promise work to preserve completion tracking and error propagation.

## Exercise Answers

Correct options:

* A Promise standardizes one eventual fulfillment or rejection.

* Callers must return or await Promise work to preserve error propagation and completion tracking.

* Promise chains, `async/await`, and combinators compose sequential and parallel asynchronous outcomes.

Incorrect options:

* Promises do not automatically cancel underlying work.

* A single Promise is not suitable for an unbounded stream of repeated events.

## TL;DR

> Promises provide a consistent way to represent one eventual result. They improve readability, error handling, sequential composition, and parallel execution. Their limitations include no automatic cancellation, no support for repeated events, potentially pending forever, and the need to explicitly return or await work to preserve error propagation.
